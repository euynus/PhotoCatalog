# PhotoCatalog 设计审查与优化

基线：`290b63c`。依据当前源码、PRD、独立自检和合成数据基准；历史审查中提到的缺失功能不直接视为当前问题。

## 结论

保留现有 SwiftUI + AppKit、SQLite、本地优先及非破坏式原件管理设计。现有四层目录和原生网格可以继续演进，无需更换框架或引入依赖。优先处理操作范围、失败语义、界面状态和重复计算。

## 本轮问题与修复

| 优先级 | 发现 | 本轮处理 |
| --- | --- | --- |
| P1 | `ImportCoordinator` 托管复制失败后回退到源文件，成功记录与实际存储位置不符 | 复制失败进入导入失败列表，不发布成功资产 |
| P1 | `HashService` 把读取异常当作正常结束，可能发布部分内容的摘要 | 读取或定位失败返回空值，不参与精确去重 |
| P1 | Compare 的全选、反选可以选中未展示照片，后续批量修改超出比较面板 | 在共享选择入口和原生菜单限制操作范围 |
| P1 | 导入会话、任务、进度和收尾写入错误被忽略，缺失记录的 UPDATE 也视为成功 | 创建和状态转换采用事务；检查更新行；写入失败停止后续文件，明确报告部分落库；拒绝恢复缺失或状态不一致的会话 |
| P2 | 全局键盘监视器将“已消费”的空返回值替换为原事件 | 保留消费结果；原生菜单跟踪期间不处理底层照片快捷键 |
| P2 | Inspector 以全库版本作为视图 identity，其他照片更新也会销毁输入草稿 | 版本作为普通输入，关键词草稿仅随照片 identity 重置 |
| P2 | 历史页为缺失哈希生成演示值，并无条件声称照片已经备份 | 缺失哈希显示未计算；只展示实际目录库备份时间 |
| P2 | ISO 未读取标准 `ISOSpeed` 键，且无效首选值会挡住后备值 | 按有效值依次读取标准字段；不回填现有图库 |
| P2 | 日期树重复转换日期，统计重复筛选、排序、解析参数 | 按拍摄日累计后构建树；范围预计算；复用列表；单遍累计参数 |
| P2 | 参数聚合在 SwiftUI body 中同步执行，较大结果会阻塞界面 | body 只读缓存，任务在后台聚合；随视图取消，按请求版本丢弃过期结果，复用未折叠的列表快照 |

## 性能证据

第一轮测量：同机、同一 Debug 构建配置，10 万条合成照片元数据、3,650 个拍摄日，连续三次取中位数。不是实际图库磁盘加载、内存或滚动性能测试。

| 操作 | 优化前 | 第一轮优化后 |
| --- | ---: | ---: |
| 日期分类 | 1,132.3 ms | 194.0 ms |
| 自定义日期筛选与列表选择校验 | 794.8 ms | 733.1 ms |
| 当前结果参数分析 | 1,666.8 ms | 576.1 ms |
| 10 张已选照片分析 | 619.7 ms | 46.8 ms |

复现：先运行 `script/build_and_run.sh build`，再运行 `.build/debug/PhotoCatalog --selfcheck --benchmark`。耗时只报告，不作为跨机器硬阈值；计数使用可执行断言检查。

第二轮将参数聚合移到后台，目标是释放主线程，而不是保证更短的总耗时。本轮复测中位数：日期分类 368.8 ms、筛选 938.6 ms、后台分析 1,010.2 ms、已选分析 48.2 ms。不同次测量存在明显波动，不能据此宣称总速度进一步提升。新增并发断言确认主 actor 在聚合未结束时仍能执行、旧请求不能覆盖新数据、取消后可重新计算。

## 保留的设计限制

- **大图库内存与主线程计算：** 参数聚合已在后台运行，但 `AppState` 仍持有全量资产，筛选、排序和日期树仍同步计算。未证明 50 万张照片的性能目标；下一步应统一数据库查询与分页，不能只替换分析页而让网格与统计口径分叉。
- **状态职责偏重：** `AppState` 同时处理目录生命周期、任务、选择和系统面板。应在下一次改动对应工作流时逐步拆分，避免一次性搬文件而不改善行为。
- **导入中断边界：** 取消在文件之间生效，当前文件处理或目录扫描不会被强行打断。已复制原件和缓存不自动删除。资产保存与源目录/终态收尾仍是两个事务，失败会明确报告部分落库；数据库完全不可写时，无法保证失败状态也能持久化。
- **发布门槛：** Swift 5 语言模式、完整 XCTest 执行、沙盒签名与权限、安装包文件类型关联、notarization 应分别验证；本轮不是发布认证。
- **已有 ISO 缺失：** 修复的是新读取路径。现有 CR3 缺失值是否来自该问题尚未验证，也未对真实照片重新扫描或回填。

- 使用本机兼容的 macOS 26.5 SDK，`script/build_and_run.sh selfcheck` 构建及断言通过；新增的事件路由、比较范围、哈希失败、托管复制失败和 ISO 回退检查均执行成功。仅剩两条本机 CLT 搜索路径的 linker 警告。
- 第二轮自检通过后台任务的失效、取消、重试和折叠堆栈范围检查；临时 SQLite trigger 覆盖会话/任务创建、进度、暂停/继续、资产与源目录保存、终态更新及缺失/不一致记录，另验证取消可释放暂停中的 worker 且不再处理下一张。
- `.build/debug/PhotoCatalog --pipeline` 通过临时目录中的导入、迁移、去重、导出、备份恢复及权限相关断言；不等同于已签名沙盒包的权限认证。
- `swift test` 已实际执行，但因本机无法解析 `XCTest` 模块而停止，完整测试套件未执行成功。
- 真实 452 张图库中，旧版反选重复执行、三张比较全选变成 452 张均已复现；新版反选一次得到 451 张，比较全选/反选仍为三张且菜单项禁用。日期菜单 Escape 仅关闭菜单，保留筛选栏。网格和分析页已核对截图。
- 历史页已显示真实目录库备份时间；Inspector 草稿 identity 修复经过代码检查，未在真实图库注入后台写入来复测草稿保持。
- 第二轮实际界面验证：全库分析 452 张、已选分析 1 张、六月分类分析 206 张，截图无布局回归。已恢复六月分类、日期树展开状态、`HR4A5002.CR3` 单选、原缩略图大小及整理面板。
- 真实照片内容和元数据未修改，也未回填旧 ISO；已恢复原来的照片选择、缩略图大小和整理面板。未推送或发布。

## 大批量 RAW 导入内存修复

- 现场：7,708 个文件，界面在 1,171 个成功文件处暂停。`vmmap` 测得进程 physical footprint 16.1 GiB、峰值 16.2 GiB，主要为仍分配的 malloc 内存且已大量换出；线程采样确认导入线程在 `ImportControl.waitIfPaused` 等待，主线程空闲。低 RSS 不代表内存已释放。
- 隔离复现：一张约 28.8 MB 的真实 CR3，通过临时符号链接建立独立文件身份，使用真实 `ImportCoordinator.importFiles`，保留返回资产；不运行界面、Vision 或 XMP。原实现第 5/10/15 次完成后为 154/297/440 MiB，第 18 次达到 526 MiB，触发检查上限。沙箱内、外均复现线性增长。
- 修复：共享导入循环逐文件使用 `autoreleasepool`，在报告进度及下一次暂停等待之前清理 Foundation/ImageIO 临时对象；首次导入、恢复、重试和增量处理共用此边界。尚未单独归因到某个框架 API，不把整个增长量称为解码位图泄漏。
- 同输入对照：40 次全部完成，逐文件采样峰值 74 MiB、预热后增长 10 MiB；扩展到 200 次，采样峰值 73 MiB、增长 7 MiB。这不是文件处理内部的瞬时峰值，也不是整批 7,708 个不同文件或所有 RAW 格式的保证。
- 验证：兼容 SDK 的 `swift build -j 2`、`--selfcheck`、`--pipeline`、`git diff --check` 通过。新增可重复的 `--import-memory-check <image-path> [20...1000]`，在 512 MiB 文件边界上限或预热后增长 128 MiB 时失败。
- 运行现场未重启、未恢复、未替换 app bundle。只读数据库确认会话与任务为 paused，持久化进度 1,170（界面 1,171），目录库仍为 452 条资产。本批资产在导入完成时整批保存，因此换新版重启后需要重新扫描和处理尚未落库的照片；原片保持不动。代码修复不能释放已暂停旧进程中的内存。
